# Перенос всех модулей в отдельные утилиты

**Цель:** 10 оставшихся модулей становятся отдельными приложениями по образцу «Не спать». Экран и лаунчер визуально не меняются.

**Основание:** обзор `docs/superpowers/specs/2026-11-06-module-survey.md` (разделы и номера ниже ссылаются на него), спека `docs/superpowers/specs/2026-11-06-hub-and-satellites-design.md`.

**Выпуск:** ничего не публикуется. Работа остаётся в локальной ветке `hub`; 0.6.0 и `awake-v1.0.0` выходят только после проверки автором на своём Mac.

## Решения по открытым вопросам обзора

Цена указана на случай, если решение окажется неверным.

| № | Решение | Цена |
|---|---|---|
| Q1 | Чек-лист до передачи рисует лаунчер, шаги приходят от утилиты, запрос разрешения делает утилита (macOS показывает её имя). Шаг, который пользователю не нужен при его настройках, необязателен | Новый канал шагов в протоколе |
| Q2 | Выход из лаунчера утилиты не останавливает. Тексты `FansView:692`, `MixerView:226` меняются только для внешнего модуля и говорят, как есть | Небольшое изменение текста у внешнего модуля: неправда на экране хуже |
| Q3 | Поля состояния добавляются только необязательными. `minHub` в каталоге для несовместимых изменений. Клиент принимает диапазон версий протокола, а не точное совпадение | Старые поля живут дольше |
| Q4 | Общая модель применяет действие к состоянию сразу и отбрасывает устаревшие ответы; частые действия (ползунки) склеиваются до последнего значения | Краткое расхождение при отказе, откат по ответу |
| Q5 | Буфер: на экран уходят счётчики и 5 обрезанных строк, как сейчас; `items` по связи не идут. Строки только пока экран открыт (аренда) | Лаунчер видит эти 5 строк; автор решает при проверке |
| Q6 | Голос: поле «Проверить» включает явный режим проверки; только в нём текст идёт в лаунчер | Узкий путь текста из утилиты, только по действию пользователя |
| Q7 | Браузер: тонкая утилита, работу по-прежнему делает `Links.app`, экран читает общий домен настроек. Без модели XPC. Перед кодом проба владельца обработчика | Отличается от остальных модулей |
| Q8 | Аренда экрана привязана к соединению и кончается при его разрыве | Нет |
| Q9 | Быстрые действия дашборда и меню идут через `moduleAction`, описаны в статусе | Шире статус |
| Q10 | Протокол модели на модуль поверх общего `RemoteModuleModel<State, Action>`, чтобы не переписывать экраны. Несколько объектов модуля сводятся в одну модель там, где это не меняет экран | Около 1000 строк пересылки |
| Q11 | Встроенный код удаляется отдельным этапом после проверки. Обращение к `.shared` в лаунчере не должно запускать работу | Лаунчер пока крупнее |

Обязательные правила из обзора: пассивная утилита остановлена (разрыв 7); `.standard` запрещён в модулях (разрыв 8, проверка в тестах); действия с силой (Стеш, Нагрузка) принимают только идентификаторы, выданные утилитой; пинги не раскрывают события (§4); кодирование связи с `sortedKeys` на обеих сторонах; передача модуля не снимает системные настройки пользователя (2.5); ни один путь не создаёт новый ключ Буфера при ошибке чтения (2.9).

## Этап 1. Общая основа, параллельно

- **F1. Связь и хост.** §6 пп. 1–4: `RemoteModuleModel`, `RemoteModulePage`, хост утилиты в Kit (`SatelliteModule`), помощники связи, протокол v3 (шаги и внимание в статусе, `stateChanged`, аренда, `quit(reason)`, диапазон версий), «пассивная = остановлена». «Не спать» переводится на всё это. Тестовый каркас из `AwakeRemoteCheck` с меткой и доменом настроек на модуль, чтобы проверки разных модулей шли одновременно.
- **F2. Общий код и настройки.** §6 пп. 5, 6, 9: перенос в Kit, `Kit.ownBundleIDs`/`Kit.isOurs` во всех местах разрыва 5, замена `.standard` в 8 модулях, защитный тест.
- **F3. Сборка и установщик.** §6 пп. 7, 8: манифест приложения, разрешения (entitlements), вложенные помощники, проверка личности каждого помощника, направление версии помощника вентиляторов (только вверх).

## Этап 2. Поверхности лаунчера

- **F4.** §6 п. 10 и таблица §7: `case` для всех модулей, цикл вместо обновления по модулям, дашборд и меню-бар от статуса, чек-лист от утилиты, «стоп при передаче». Вид без изменений; проверка пикселями.

## Этап 3. Модули

Каждый в своём worktree от коммита после F4. Правит только `Modules/<X>`, `Apps/<X>`, `Remote<X>`, свои тесты. Образец и правила: Task 10 первого плана и этот файл.

- **Звук** первым и один: проверка основы. По его итогам правится основа.
- **Одновременно:** Мышь, Микшер, Стеш, Клавиатура, Нагрузка.
- **Параллельно им, но по очереди между собой** (правят `build.sh`, `UpdateBundle`, `install.sh`): Браузер, Голос, Вентиляторы.
- **Буфер:** после Голоса и пробы ключа. Проба только на тестовой записи, с `kSecUseAuthenticationUIFail`, настоящий ключ не трогать.

Для каждого: своя проверка безопасности, контрольные поломки тестов, сравнение пикселей встроенного и внешнего экрана. Высокий риск (Клавиатура, Браузер, Буфер, Вентиляторы): отдельная проверка другим агентом.

## Этап 4. Итог

Полный прогон всех проверок и `run-hub-e2e.sh`, замер главного потока в `-O` (встроенный, внешний, зависшая утилита), обзор всей ветки, пилот через `scripts/build-pilot.sh`, список для ручной проверки автором.

## Очередь сборок

Агентов сколько угодно; ограничение в памяти Mac. Команды сборки и проверок запускаются через очередь (`buildq`): `build` с числом мест из файла, которое меняет контроллер по замеру, и `stand` по одному для проверок с общими метками. Журнал ожидания, длительности и свопа в `buildq.csv` служит замером лимита.
