# Проба обработчика ссылок: две копии с одним bundle id

**Вердикт: переход без момента, когда ссылку некому открыть, возможен, и выбор обработчика не требует ни подтверждения, ни записи.** Обработчик хранится как id, без пути. При удалении одной копии вторая получила ссылку сразу, без диалога и без `LSRegisterURL`. Когда копия вернулась, обработка восстановилась сама.

Три вещи, которые надо учесть в плане:

1. **Новая версия не перехватывает ссылки, пока её ни разу не запускали через LaunchServices.** Копия v1, которую уже запускали, побеждает незапущенную v2.
2. **Запущенная копия получает ссылку раньше выбранной.** Настоящий помощник после ссылки не выходит, поэтому старый будет получать ссылки, пока его не остановят.
3. **В 19% холодных запусков заглушка не получила ссылку, хотя `open` вернул успех.** Причина не найдена. См. раздел ниже, это надо проверить на настоящем помощнике.

http и https в пробе не трогались, всё про них ниже помечено как вывод.

## Условия

- macOS 26.2 (25C56), arm64. Только id `local.utilitumus.test.linkprobe` и схема `utilitumus-linkprobe`.
- Запуск: `open`. Регистрация: `LSRegisterURL`. Снятие: `lsregister -u`. Запись обработчика: `LSSetDefaultHandlerForURLScheme`.
- Папки: `/Applications/LinkProbe/` (полный прогон) и `~/Library/Application Support/utilitumus-linkprobe/` (только вопрос 1). Заглушки лежали на уровень-два глубже, чем будут настоящие копии.
- Подпись: ad hoc. Сертификат отпал: см. «Что не проверено».
- Диалоги отслеживались по списку окон. Ни одного окна `CoreServicesUIAgent`, `UserNotificationCenter`, `launchservicesd` не появилось.
- «Открылась» в таблицах значит, что заглушка записала ссылку в журнал.

**`/private/tmp` не годится для таких проб.** Всё под ним получает флаг `in-temp-dir`, и такие копии обработчиками не считаются (−10814). Контроль подтвердил причину: та же заглушка вне `/private/tmp` работает. Следствие: сборка из worktree под `/private/tmp` браузером по умолчанию работать не будет (вывод).

## 1. Какую копию открывает LaunchServices

Выбор стабилен, чужая копия ни разу не открылась. 2–3 повтора на случай, по 4 открытия, в обеих папках; результаты совпали.

Порядок правил (выводится из наблюдений, документации на него нет):

| Приоритет | Правило | Доказательство |
|---|---|---|
| 1 | Запущенная копия | Проигравшая запущена: 4 из 4 в App Support; в `/Applications` 3 из 4 (первую взяла предыдущая копия, ещё не завершившаяся). Вышла — выбор вернулся |
| 2 | Запущенная хотя бы раз через LaunchServices важнее незапущенной | v1 запущена, v2 нет → v1. После первого запуска v2 → v2 (3 прогона) |
| 3 | Больший `CFBundleVersion`, сравнение по числам | 0.5.10 > 0.5.9. При конфликте 2.0/1 и 1.0/2 побеждает 1.0/2 |
| 4 | Путь по алфавиту | `Aa` раньше `Zz`; `z/A.app` проигрывает `B.app`; `a/b/…/T.app` выигрывает у `Hub.app/…/N.app` |

Флаг в базе у незапущенной копии — `launch-disabled`, после запуска он исчезает. Что правило 2 работает именно через него — вывод.

**Не влияют:** порядок регистрации, порядок создания, дата изменения, глубина пути, вложенность, повторная регистрация (`LSRegisterURL`, `lsregister -f`), `CFBundleShortVersionString`, последний запуск (когда обе уже запускались).

**`setDefaultApplication(at:)` не закрепляет копию.** Вызов с путём проигравшей вернул успех, выбор не изменился.

## 2. Удаление открытой копии

Измерено в `/Applications/LinkProbe`.

| Случай | Следующий `open` |
|---|---|
| Удалена выбранная, без снятия регистрации (2 повтора) | сразу другая копия, t=0 |
| Снята регистрация и удалена | сразу другая копия |
| Удалена вложенная, выбранная | сразу копия верхнего уровня |
| Удалена невыбранная | без изменений |
| Выбранная перенесена в другую папку | первый `open` без события, через 1 с другая копия |
| Выбранная удалена, пока работает (1 прогон) | первый `open` без события, второй — другая копия |

Диалога выбора не было. `LSRegisterURL` выжившей не нужен: перед вызовом ссылка уже шла ей. Ссылки без события могут быть той же потерей, что описана ниже, различить их не удалось.

**Удаление и перенос в Корзину ведут себя одинаково** (`FileManager.trashItem`, 2 сценария):

| | Одна копия | Две копии |
|---|---|---|
| Удалена | −10814 с t=0 до 8 с | сразу другая копия |
| В Корзине | −10814 с t=0 до 8 с | сразу другая копия |

Копия в Корзине получает флаг `trash` и не выбирается, из Корзины ничего не запускается. Запись о ней в базе остаётся и после очистки Корзины, но ни на что не влияет: её не возвращают ни `open`, ни `NSWorkspace`.

## 3. Удаление обеих

- `open` — код выхода 1, −10814, держится все 10 с наблюдения. Диалога нет, но запускался только `open`.
- Запись об обработчике остаётся: и в базе, и в `com.apple.launchservices.secure.plist`, даже при нуле копий.
- `LSCopyDefaultHandlerForURLScheme` и `urlForApplication(toOpen:)` при этом возвращают `nil`. **По API нельзя отличить «не назначен» от «назначен, но копии нет».**
- Копия вернулась по тому же пути: работает при первом же `open`, без регистрации и без `setid` (`/Applications` видит её сам).
- Копия появилась по новому пути: первый `open` −10814, через 1 с работает, тоже без `setid`.

**Вывод для http/https, не проверялось:** запись переживёт удаление копий и вернётся вместе с ними, подтверждение не понадобится. Что станет со ссылкой, пока копии нет, неизвестно: у http/https, в отличие от вымышленной схемы, есть другие кандидаты, например Safari. Проверка требует второго id, бриф его запрещает. Закладываться на автоматический переход на другой браузер нельзя.

## 4. Замена на месте

- Обработчик сохраняется во всех случаях: `replaceItemAt` на новую и на старую версию, удаление с переносом. Плист и выбранная копия те же, пути нет.
- После замены 1.0→2.0 без регистрации сразу открылась 2.0 (`/Applications` замечает сам).
- Откат 2.0→1.0 и удаление с переносом на 3.0: обработчик и выбранная копия на месте, но все `open` в этих шагах прошли без события, **какая версия получила бы ссылку, не наблюдалось**.
- Две копии: A 1.0 заменена на 2.0, B 1.5. Если B уже запускалась, выбор остаётся на ней и после `LSRegisterURL`. Если не запускалась ни одна, сразу A. Это то же правило 2.
- Не проверено: теряет ли статус «запускалась» уже запускавшаяся копия после замены.

## 5. Вложенная копия и копия верхнего уровня

**Вложенность сама по себе не влияет на выбор.** N — вложенная, T — верхнего уровня, порядок регистрации в обе стороны, 2 повтора:

| Случай | Открылась |
|---|---|
| Равные версии, `Hub.app/…/N.app` и `T.app` | N (путь) |
| N 2.0, T 1.0 | N |
| N 1.0, T 2.0 | T |
| Равные версии, `a/b/…/T.app` | T (путь) |
| **Форма как в жизни:** `Utilitumus.app/Contents/Helpers/N.app` и `Utilitumus/T.app`, равные версии | **N**, при обоих порядках |

Отличие в регистрации:

- Копия прямо в папке под `/Applications` становится известна сама за 1–2 с.
- Вложенная сама не регистрируется, регистрация внешнего бандла её тоже не подхватывает: −10814. Внешняя заглушка была без id и без подписи, у настоящего центра может быть иначе. Нужен прямой вызов, который уже есть (`UtilitumusApp.swift:294`).

## Прогон перехода

Вложенный N 1.0, утилита T, `/Applications/LinkProbe`, по одному прогону на версию утилиты. Везде `default=id`.

| Шаг | T 1.0 | T 2.0 |
|---|---|---|
| Только центр | N | N |
| Утилита установлена и зарегистрирована | N | **N** (незапущенная) |
| Центр при запуске снова регистрирует помощника | N | N |
| Обновление центра убрало помощника, без снятия регистрации | T, t=0 | T, t=0 |
| Откат центра вернул помощника | T | все 3 `open` без события, выбрана T |
| Утилиту удалили, помощник остался | N, t=0 | N, t=0 |
| Удалили и помощника | −10814 | −10814 |
| Утилиту поставили заново, без записи обработчика | T | T |

Разрывы только там, где копий нет вообще.

## Потеря ссылки при холодном запуске

- 113 из 605 запусков (19%): заглушка запустилась, `open` вернул 0, а ссылка не пришла за 6 с жизни процесса. Ещё 37 процессов завершены принудительно при очистке и не считаются.
- Там, где ссылка дошла, обычно 12 мс от запуска, максимум 5,4 с.
- Попадались серии: семь подряд в прогоне вопроса 4.
- **Причина не найдена.** Обработчик ставится в `applicationWillFinishLaunching`, как в настоящем помощнике (`LinkHelper/main.swift:8-11`). Машина была загружена параллельными задачами, а заглушка выходит сразу после ссылки. Это может быть особенностью заглушки, но может и не быть.
- Настоящий помощник обычно уже работает, поэтому холодных запусков у него мало. Но обновление и переход их как раз создают. Проверить отдельно, до переключения.

## 6. Порядок перехода

Измеренные шаги отмечены, остальное — вывод.

1. **Подготовка.** Исправить `moduleDisabled` (`BrowserCatalog.swift:47`) и `BrowserHelper.appURL` (`:50-53`): по правилам выше ссылку может получить любая копия, поэтому обе должны вести себя одинаково. Проверить потерю ссылки на настоящем помощнике.
2. **Выпуск N: центр с помощником и утилита с тем же id.** `LSRegisterURL` утилиты, **без `setDefaultApplication`**. Пока жив помощник, ссылки идут ему (измерено при равных версиях). Если версия утилиты выше, переключение случится при первом её запуске через LaunchServices. Стартует ли это от запуска агентом launchd, не проверено, поэтому моментом переключения не считать ни установку, ни запуск агента.
3. **Выпуск N+1: центр без помощника.** Обновляться на него только если утилита установлена и `urlsForApplications(withBundleIdentifier:)` её видит; иначе сначала поставить утилиту. Перед заменой **остановить работающий старый помощник**: запущенная копия получает ссылку раньше выбранной. После этого утилита принимает ссылки сразу (измерено, t=0). `LSRegisterURL` при запуске (`UtilitumusApp.swift:294`) вести на утилиту, а не на путь внутри центра.
4. **Удаление утилиты через центр** (сейчас этого шага нет, `SatelliteInstaller.remove`):
   - если обработчик наш и другой копии нет, вернуть браузер: `Browser.Fallback`, если установлен, иначе Safari;
   - macOS покажет подтверждение;
   - удалять бандл только когда `urlForApplication(toOpen:)` вернул другой id;
   - отказ — не удалять и объяснить. `try?` из `SetupStep.swift:97` здесь не годится.
5. **Обновление утилиты на месте:** без возврата браузера, запись сохраняется (измерено). Сейчас обновление и удаление идут через один `quit`, развести.
6. **Удаление мимо центра** (Корзина, `rm`): возврат невозможен. При запуске центр не сможет понять это через API (измерено: `nil`). Нужен свой след: хранить в общих настройках, что обработчик наш, и сверять с `urlsForApplications(withBundleIdentifier:)`. Пусто — предложить вернуть браузер.
7. **Откат.**
   - Центра: помощник возвращается, ссылки не теряются (измерено: обработка продолжилась утилитой).
   - Утилиты при центре N+1: копия одна, замена на месте.
   - **Ловушка:** если остаётся более новая копия, которую уже запускали, ссылки останутся у неё и после отката другой (правило 3). Откат должен убирать или заменять такую копию.
   - Утилита удалена и помощника нет: обрыв до возврата браузера или переустановки. Запись сама вернётся с копией.

**Подтверждение macOS.** Пока id тот же, записывать ничего не нужно: обработка возвращалась без `setid` (измерено на вымышленной схеме). Значит, при переходе диалога быть не должно (вывод). Он понадобится только при возврате браузера в п. 4. На вымышленной схеме диалог не появляется, поэтому сам диалог не проверялся: сколько раз он покажется на http и https, что будет при повторной установке того же id и какую ошибку вернёт отказ, неизвестно.

## Что не проверено

- http, https и настоящий диалог подтверждения.
- Переход ссылки на браузер с другим id: только один id разрешён.
- Клик по ссылке из приложения при отсутствии обработчика: только `open`, возможен диалог.
- Вопросы 2–5 вне `/Applications`: прогон в App Support остановлен по лимиту времени, там только вопрос 1.
- Снимается ли `launch-disabled` от запуска через launchd. От этого зависит момент переключения на утилиту.
- Замена уже запускавшейся копии: сохраняется ли статус.
- Влияние подписи: сертификат против ad hoc. Подпись сертификатом зависла за чужим окном `SecurityAgent`: оно появилось в 21:59:36, до этого этапа, в очереди стоял чужой `codesign`. Окно не трогал, к концу пробы его уже не было.
- Настоящий внешний бандл центра с id и подписью.
- Перетаскивание в Корзину в Finder (измерен `trashItem`).
- Настоящие пути: прямо в `/Applications`, а не во вложенных папках.
- macOS 14 и 15.

## Состояние после пробы

- http и https до и после: `local.utilitumus.links`, **без изменений**.
- Обе папки удалены. Записей приложений с тестовым id в `lsregister -dump` нет, включая Корзину. Процессов нет. Контрольный `open` возвращает −10814.
- **Остаток:** запись обработчика вымышленной схемы в базе и плисте. Она ни на что не указывает, а убрать её можно только правкой настоящего плиста или сбросом базы, это запрещено.
- Настоящие приложения и `/Applications/Utilitumus*` не трогались. В репозитории ничего не менялось, этот файл не закоммичен.
- Журналы и код пробы лежат в `probe-links/` в scratchpad.
- Лимит превышен примерно на 9 минут: потери ссылок удлиняли прогоны, а прогон перехода надо было довести до конца.
